# P1-04 面向多源调用链的应用-数据库-缓存拓扑图构建方法

- 状态：DRAFT
- 优先级：P1
- 风险：中
- 主要近似来源：通用架构（主）+ 行业常规（次）

## 1) 专利名称

一种面向多源调用链的应用-数据库-缓存拓扑图构建方法。

## 2) 背景技术

- 一条完整调用链中通常同时存在客户端请求、应用服务、数据库访问、缓存访问和远程调用等多类节点，若缺少统一建模，前端往往只能看到离散事件，难以快速识别真实链路结构。
- 现有拓扑构建方案常把“节点展示”和“节点身份归一”混为一体，导致同一数据库、同一远程服务或同一应用被重复渲染为多个节点，图谱噪声较大。
- 多次 SQL、Dubbo 或 Redis 调用若不做边级合并，图中容易产生大量重复边，影响可读性，也难以稳定表达调用强度。
- 现有技术通常缺少“多源 Trace 节点 -> 节点身份归一 -> 同边合并计数 -> 节点异常态标注 -> 图对象输出”的统一构图机制。

## 3) 现有缺陷

- 节点身份规则不统一，同一资源容易重复出图。
- 多源事件缺少统一汇聚路径，图谱与详情数据口径不一致。
- 边关系未按起点、终点和事件类型稳定合并，调用强度无法准确表达。
- 节点异常信息未统一映射到图展示状态，排障效率低。

## 4) 技术方案

- 统一接收 HTTP、应用、数据库、Redis、远程调用等多源 Trace 节点。
- 依据节点类型和身份规则完成客户端、应用、数据库和缓存节点归一。
- 对 SQL、CKSQL、Dubbo、Redis 等事件按事件类型构建有向边。
- 对相同起点、终点、事件类型的边进行合并并累加调用次数。
- 将错误集合统一映射为节点状态，并输出可交互图对象。
- 支持图节点与节点详情视图使用同一来源 Trace 节点集合，避免前后口径漂移。

### 变量及字段说明

- `N` 表示用于构图的 Trace 节点集合；`traceId` 表示调用链标识；`traceNodeId` 表示 Trace 内单个节点标识。
- `requestUrl` 表示请求地址；`User-Agent` 表示客户端标识；`nodeId` 表示图节点唯一标识；`title` 表示图节点标题；`name` 表示图节点显示名称。
- `appId` 表示应用标识；`addressIp-port-dbName` 表示“数据库地址-端口-库名”联合标识；`host@port` 表示 Redis 主机与端口联合标识；`count` 表示聚合后的调用次数。
- `errors[]` 表示节点错误集合；`state` 表示节点状态；`normal` 表示正常状态；`error` 表示异常状态。
- `nodes[]` 表示输出图节点数组；`edges[]` 表示输出图边数组；`defaultNode` 表示前端默认聚焦节点。

## 5) 本发明创造的优点、有益的技术效果

- 提升多源调用链在图视图中的可读性和稳定性，减少重复节点和重复边。
- 将应用、数据库、缓存和远程服务纳入统一图谱口径，便于故障传播路径定位。
- 通过边计数和节点状态标注，增强图谱的可解释性和诊断价值。
- 使图谱展示与节点详情共享同一 Trace 数据源，降低重复解析成本。

## 6) 权利要求草案

### 独立权利要求1（一句话）

一种调用链拓扑构建方法，其特征在于：将多源 Trace 节点按客户端、应用、数据库、缓存和远程调用类型归一建模，并依据事件类型构建有向边，对相同起点、终点和事件类型的边合并计数，同时根据节点错误信息标记状态后输出可交互拓扑图对象。

### 从属权利要求2-5

- 权利要求2：根据权利要求1所述的方法，其特征在于，客户端节点依据根请求节点生成，应用节点依据应用标识聚合，数据库节点依据地址、端口和库名联合聚合。
- 权利要求3：根据权利要求1所述的方法，其特征在于，Redis 节点依据主机和端口联合聚合，远程调用节点依据远端应用信息映射到目标应用节点。
- 权利要求4：根据权利要求1所述的方法，其特征在于，同一起点、终点和事件类型的边仅保留一条，并通过计数值表示调用频次。
- 权利要求5：根据权利要求1所述的方法，其特征在于，图节点状态依据对应错误集合是否为空标记为正常或异常状态。

### 技术关键点和欲保护点

- 技术关键点：多源节点统一输入、节点身份归一、SQL 事件聚合、同边合并计数、异常状态标注、图对象输出。
- 欲保护点：以“Trace 节点归一 -> 节点聚合 -> 边构建 -> 边计数合并 -> 节点状态标注 -> 图对象输出”的处理链保护拓扑图生成核心机制。

## 7) 发明内容

本方案由以下八个部件组成，各部件顺序衔接，共同完成从多源 Trace 节点到可交互拓扑图对象的构建过程。

### 部件一：节点来源部件

**职责**：读取构图所需的统一 Trace 节点集合，并保证图谱与详情共用同一份数据源。

具体而言，该部件可按会话、实时缓存或持久化快照的优先顺序获取 `N={n1,n2,...,nk}`。数据上，例如 `traceId=T20260325_001` 时若读取到 `13` 个原始节点，则图谱和节点详情都围绕这 `13` 个节点展开，避免不同页面口径不一致。

### 部件二：根节点识别部件

**职责**：识别根请求节点并构造客户端入口节点。

具体而言，该部件把 `traceNodeId="0"` 且类型为 HTTP 的节点识别为根请求节点，提取 `requestUrl` 和 `User-Agent`，生成唯一客户端节点 `user-agent`。数据上，例如请求地址为 `/api/order/create`、浏览器为 `Chrome` 时，可生成 `nodeId=user-agent`、`title=/api/order/create`、`name=Chrome`。

### 部件三：节点归一部件

**职责**：按应用、数据库、Redis 和远程调用规则把多源事件归并为稳定图节点。

具体而言，该部件以 `appId` 归一应用节点，以 `addressIp-port-dbName` 归一数据库节点，以 `host@port` 归一 Redis 节点，并把远程调用映射到目标应用节点。数据上，例如数据库访问目标为 `10.0.0.8:3306/order_db` 时，图中始终只保留一个 `10.0.0.8-3306-order_db` 节点。

### 部件四：SQL 聚合部件

**职责**：把同一数据库上的重复 SQL 事件收敛为少量聚合语义对象，减少图谱噪声。

具体而言，该部件按数据库地址、端口、库名和 SQL 文本构造分组键，对同一 SQL 的执行次数、参数和动作语义做累加。数据上，例如 `select * from t_order where id=?` 在同一 Trace 中被执行 `3` 次时，该部件只保留 `1` 个 SQL 聚合对象，并把 `count` 记为 `3`。

### 部件五：关系构建部件

**职责**：依据 HTTP、Dubbo、SQL、Redis 等事件类型建立有向边关系。

具体而言，该部件把 HTTP 根事件映射为“客户端 -> 应用”边，把 Dubbo 映射为“应用 -> 应用”边，把 SQL/CKSQL 映射为“应用 -> 数据库”边，把 Redis 事件映射为“应用 -> 缓存”边。数据上，例如 `order-service` 调用 `inventory-service` 的 `3` 次 Dubbo 事件会先形成 `3` 条原始边候选。

### 部件六：边合并计数部件

**职责**：对相同 `(from,to,type)` 的边执行去重与计数累加，稳定表达调用强度。

具体而言，该部件对重复边只保留一条，并将 `count` 增加到边对象上。数据上，若 `order-service -> inventory-service` 的 Dubbo 调用共 `3` 次，图中只保留一条 `count=3` 的应用间边；若应用到数据库的 SQL 调用共 `5` 次，则也只保留一条 `count=5` 的数据库访问边。

### 部件七：状态标记部件

**职责**：把节点错误集合统一转换为图展示状态，支撑异常高亮。

具体而言，该部件当节点 `errors[]` 为空时标记为 `normal`，非空时标记为 `error`，并把错误详情保留在节点扩展字段中。数据上，例如数据库节点 `10.0.0.8-3306-order_db` 若累计有 `2` 条 SQL 错误，则会被直接标记为 `state=error`。

### 部件八：图输出部件

**职责**：汇总节点、边、默认节点和标题信息，输出前端可直接渲染的图对象。

具体而言，该部件统一产出 `nodes[]`、`edges[]`、`defaultNode` 和 `title`，使前端无需再重复解析原始 Trace 节点。数据上，例如一条原始调用链包含 `13` 个事件节点，归一后可能只输出 `5` 个图节点和 `3` 条边，图结构更稳定、可读性更高。

## 8) 具体实施例

### 实施例：订单创建链路的应用-数据库-缓存拓扑构建

某条 Trace 的原始输入数据如下：

| 项目 | 数值 |
|---|---|
| `traceId` | `T20260325_001` |
| HTTP 根节点数 | `1` |
| 应用节点数 | `2` |
| SQL 事件数 | `5` |
| Redis 事件数 | `2` |
| Dubbo 事件数 | `3` |
| 数据库 | `10.0.0.8:3306/order_db` |
| Redis | `10.0.0.9:6379` |
| 远程应用 | `inventory-service` |

按各部件执行后的处理过程如下：

1. **节点来源部件**读取该 Trace 的 `13` 个原始节点，并把这批节点同时提供给图谱和详情页面。
2. **根节点识别部件**识别 HTTP 根节点，生成客户端节点 `user-agent`，标题为 `/api/order/create`。
3. **节点归一部件**把应用节点收敛为 `order-service` 和 `inventory-service` 两个应用节点，把数据库事件归一到 `10.0.0.8-3306-order_db`，把 Redis 事件归一到 `10.0.0.9@6379`。
4. **SQL 聚合部件**把 `5` 条 SQL 事件按数据库和 SQL 文本归并为数据库语义对象，避免同一数据库被重复渲染。
5. **关系构建部件**生成原始边集合：客户端到应用边、应用到数据库边、应用到 Redis 边，以及 `order-service -> inventory-service` 的 `3` 条 Dubbo 候选边。
6. **边合并计数部件**把重复边收敛为单条边并叠加计数，形成 `order-service -> inventory-service, count=3` 和 `order-service -> order_db, count=5` 等结果。
7. **状态标记部件**检查节点错误集合，若数据库节点累计 `2` 条错误，则将 `10.0.0.8-3306-order_db` 标记为 `error`。
8. **图输出部件**输出如下图摘要：

| 类型 | 标识 | 数量/状态 | 说明 |
|---|---|---:|---|
| 客户端节点 | `user-agent` | 1 | 请求入口 |
| 应用节点 | `order-service`、`inventory-service` | 2 | 按 `appId` 聚合 |
| 数据库节点 | `10.0.0.8-3306-order_db` | 1 / `error` | `5` 次 SQL 访问归并 |
| Redis 节点 | `10.0.0.9@6379` | 1 / `normal` | `2` 次 Redis 访问归并 |
| 应用到应用边 | `order-service -> inventory-service` | `count=3` | Dubbo 边合并 |
| 应用到数据库边 | `order-service -> order_db` | `count=5` | SQL 边合并 |

本实施例中，系统先把多源事件统一归一为稳定节点，再把重复边合并为带计数的边对象，最后把异常信息映射到节点状态上。这样用户在图上看到的不是 13 个离散事件，而是能够直接解释调用关系和异常位置的稳定拓扑结构。
